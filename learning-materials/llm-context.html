Concept · Study Note 02

大模型的上下文（Context）

读四节，答六题。每个论断都能点回原始出处验证。
01 / 个人解释

一句话

上下文 = 模型每次采样时能看到的全部 token；它是有限资源，且越堆越"糊"。

我的理解：上下文窗口像一张只能摊开一页的书桌——系统提示、工具说明、对话历史、检索来的资料全都要摆在这一页上。东西摆太多，注意力就被摊薄，重要的反而看不清。所以关键动作不是"多放"，而是"放对"：每次只放当前这一步最需要的高信号内容。
context rot 原文定义："as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"——是性能梯度（gradient），不是硬悬崖。

出处 · Anthropic《Effective context engineering for AI agents》（2025-09）↗

02 / 核心机制

注意力预算：为什么"放对"比"放多"重要

上下文工程（context engineering）是提示工程的演进：从"怎么写一条指令"，变成"每一轮推理该把哪些信息放进窗口"的持续筛选。

三种技术对应三种"窗口装不下"的情况：装不下历史、装不下状态、装不下探索过程。

出处 · Anthropic §Compaction / §Structured note-taking / §Sub-agent architectures ↗

03 / 应用场景

一个具体场景：编程智能体的一场长会话

一个智能体连续工作几小时修代码，上下文早就爆了。原文（Claude Code）的解法组合拳：

压缩历史把几十轮工具输出摘要保留——架构决策、未解决的 bug 留下，冗余输出丢弃（tool result clearing）
记 NOTES.md关键进展写成结构化笔记持久保存，窗口重置后先读笔记再继续
派子代理让子代理去通读整个代码库（数万 token），只把 1-2k token 的结论带回主上下文

每一招都在回答同一个问题：这一步，模型真正需要看到的是什么？

04 / 易混淆与使用边界

两个最容易搞混的点

上下文 ≠ 记忆 短期记忆借上下文窗口实现，但长期记忆靠外部向量库等窗口之外的存储。窗口清空后，"记得住"靠的是能把外部存储的内容再取回来。
窗口更大 ≠ 效果更好 大窗口只解决"装得下"，不解决"看得清"——context rot 依然存在（成因：n² 注意力关系被摊薄、训练数据以短序列为主、位置编码插值退化）。工程目标始终是高信号的小集合，不是无限大杂烩。
